# ADR-0024: EV3RT 1.1 on the EV3 brick (C bridge app, serial link, Bluetooth PAN upload)

- **Status:** accepted (owner decisions 2026-10-08)
- **Date:** 2026-10-08

## Context
The owner runs **EV3RT 1.1** (TOPPERS/HRP2-based real-time OS, 2021) on the EV3 brick instead of ev3dev. EV3RT
apps are C, built with the EV3RT SDK and `arm-none-eabi-gcc`; there is no Linux, no Python, no USB networking.
The EV3RT API offers serial ports as files (`ev3_serial_open_file`: UART on sensor port 1 at 115 200 baud,
USB CDC, Bluetooth SPP) and the loader accepts apps over Bluetooth PAN (`POST http://10.0.10.1/upload`).

## Decision
- **Same frames, new transport**: the rf-proto v1 frames stay unchanged; serial links use COBS framing with a
  `0x00` delimiter (self-synchronising; EV3RT may print emergency logs on port 1). ev3dev keeps UDP. The
  bundle selects `ev3.os` and `ev3.link`; ev3dev remains supported (owner decision).
- **One C library** (`ev3rt/common`, C99, no EV3RT dependency) holds frames, COBS and the bridge logic; a thin
  `app.c` binds it to the EV3RT API. The library is unit-tested on the host (cc, sanitizers); the app is
  syntax-checked against stub headers locally and cross-compiled with the real SDK in CI.
- **Build** runs EV3RT's own `make app=…` in the user's SDK (path from `RF_EV3RT_SDK`); RaceForge only stages the
  sources and a generated `rf_config.h`. **Upload** sends the same HTTP request as EV3RT's `make upload`.
- **No new Python dependency** (httpx is already used). The EV3RT SDK and `arm-none-eabi-gcc` are build tools
  outside the repo (TOPPERS license, permissive; not redistributed by RaceForge).
- Standalone mode (controller in C on the EV3, spec 0012) reuses the library.

## Consequences
- Wiring the UART needs a custom cable (sensor port 1 ↔ board UART, 3.3 V); a person checks it before first use.
- Ultrasonic resolution drops to 1 cm under EV3RT; the sim models it.
- Race mode refuses the Bluetooth link; UART and USB CDC are wired and race-legal.
