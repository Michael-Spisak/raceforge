# Spec 0008: Frontend shell v1 — desktop/browser app with parts browser, 3D car view and sim viewer

- **Status:** approved (2026-10-08)
- **Owner:** @Michael-Spisak
- **Plan section:** docs/PLAN.md "Tech stack" (Front-end, Desktop shell, Python engine install), §1 (Construct),
  §3 (Simulate), §9d (non-functional targets)
- **Related ADRs:** ADR-0004 (Electron + React + three.js); new ADR-0018 (frontend toolchain + local engine API)
- **Depends on:** Specs 0001–0004 (data, quick-start, simulation, controllers)

## Purpose
The first version of the RaceForge user interface. It has to be visible and useful early: the team can browse
parts, configure a quick-start car and see it in 3D, run a controller in a generated corridor and **watch the
simulation**, and replay recorded runs. It sets up the structure that the full editor, track editor, live
screen and backend features will build on later.

## Scope
- In scope:
  1. **Local engine API** (`raceforge.api` + `raceforge.server`): a FastAPI app started on `127.0.0.1` by the
     desktop shell (or by `raceforge ui` in a terminal). This is the only way the UI talks to Python code
     (AGENTS.md architecture rule). REST for requests, WebSocket for streaming sims.
  2. **Frontend** (`frontend/`): TypeScript + React + React Three Fiber, Vite build, react-i18next (DE + EN,
     defaults to the system language), light/dark theme following the system, colour-blind-safe palette.
  3. **Electron shell** (`frontend/electron/`): one window with tabs; starts and stops the Python engine as a
     sidecar; shows a clear error if the engine does not start. First-start engine bootstrap via uv is
     **out of scope for v1** (dev setup: `uv sync` already done); the installer spec comes later.
  4. **Browser mode:** the same UI opens in a normal browser when `raceforge ui --browser` is used.
  5. Screens (v1):
     - **Start page:** links to the tabs, engine status, version.
     - **Parts:** searchable catalogue (from spec 0002) with category filter, mass, connectors and a 3D preview
       of the real LDraw geometry.
     - **Construct (quick-start):** form for `QuickStartParams` with validation messages from the engine,
       3D view of the generated car (real LDraw parts, coloured by function), derived data panel (mass, CoG,
       wheelbase, track, turning radius, top speed, runtime) and the plausibility warnings, export buttons
       (`assembly.json`, `car.mpd`, `car.xml`).
     - **Simulate:** pick controller template or file, corridor seed / loop or open / length, laps, opponents;
       start, pause, stop; **3D view of the corridor and cars** with live trail, camera follow/top view, sensor
       rays toggle (ultrasonic cones, LiDAR points), lap times, contact events list, current controller state
       and emitted channels; speed control (1×, 2×, 5×, max).
     - **Replay:** open an `.mcap` recording; timeline scrubber; plots of steering, speed, distances; state
       timeline.
  6. Navigation presets for the 3D views: **Blender / BrickLink Studio / Fusion** (plan §1), units mm + studs.
- Out of scope (later specs): full brick editor (placement, snapping, submodels), custom-part import, track
  editor and scan pipeline, live car screen (needs the car runtime telemetry), backend login/sync/versions,
  collaboration, MCP, reports, command palette and guided tours, installers and auto-update, MuJoCo
  WebAssembly (v1 streams simulation state from the Python engine instead).

## Engine API (contract — human-owned)
REST (JSON, OpenAPI generated by FastAPI and snapshot-tested; TypeScript client generated from it):
| Method | Path | Purpose |
|---|---|---|
| GET | `/api/v1/health` | engine version, LDraw library available? |
| GET | `/api/v1/parts?query=&category=` | catalogue entries (key, name, category, mass, connectors, ldraw_id) |
| GET | `/api/v1/quickstart/schema` | JSON Schema + defaults + valid options of `QuickStartParams` |
| POST | `/api/v1/quickstart` | params → `{assembly, derived, warnings, scene}` or field errors (422) |
| GET | `/api/v1/quickstart/export/{kind}` | `assembly.json` / `car.mpd` / `car.xml` for posted params |
| GET | `/api/v1/controllers` | templates + recently used controller files |
| POST | `/api/v1/corridor` | `CorridorParams` → track + scene description |
| POST | `/api/v1/replays` | open an MCAP path → frames summary |
| GET | `/ldraw/{path}` | static LDraw files from the local library cache (for three.js `LDrawLoader`) |

WebSocket `/api/v1/sim` (one simulation per connection): client sends `start` (controller, params, corridor,
laps, opponents, seed, speed), `pause`, `resume`, `stop`, `speed`; server streams `scene` once (static track
geometry + car bodies/geoms), then `frame` messages at ≤ 30 Hz (simulation time, body poses per car, ego
readings incl. LiDAR points, command, controller state + channels, progress, new events) and a final `result`.

**Scene description:** list of primitives (box/cylinder/plane with pose, size, colour, surface class) and, for
cars, body → part list (LDraw id + pose) so the UI can draw real LEGO parts and move them with the body poses.

## Non-functional targets (plan §9d)
- Smooth 3D (≥ 50 FPS) for the quick-start car and a 60 m corridor with 4 cars on a MacBook Air M2.
- Sim stream latency engine → screen < 100 ms; UI never blocks while the engine computes.
- Engine start → UI usable < 5 s on a MacBook Air M2 (excluding first-run installation).

## Acceptance criteria (→ tests)
- [ ] AC1: Engine API endpoints covered by pytest (FastAPI TestClient); OpenAPI schema snapshot test fails on
      any contract change; the TypeScript client is generated from it in CI and type-checks.
- [ ] AC2: `POST /quickstart` returns the same derived data as the CLI for the same parameters; invalid params
      return 422 with the nearest-valid hints from spec 0002, shown next to the form field.
- [ ] AC3: Sim WebSocket: start → scene → frames → result for a template controller; pause/resume/stop work;
      the run's result equals a headless `run_race` with the same seed (determinism).
- [ ] AC4: Frontend unit tests (Vitest) for state stores, form validation display, i18n (no missing keys in DE/EN)
      and the frame interpolation used by the 3D view.
- [ ] AC5: Playwright e2e against the real engine: open app → Construct → change wheelbase → 3D view updates and
      derived panel changes → Simulate 1 lap with `centering.py` → lap time shown → Replay opens the recording.
- [ ] AC6: Electron: app starts the engine, shows the start page, and quits the engine on close (smoke test in
      CI on macOS, Windows, Linux).
- [ ] AC7: `raceforge ui --browser` serves the built frontend and opens the default browser.
- [ ] AC8: ESLint, `tsc --noEmit` strict, Vitest, Playwright and the existing Python gates are part of
      `scripts/check.sh` / CI.
- [ ] AC9: Manual check by the owner: the quick-start car looks right in the Construct view, and a simulated
      race is understandable in the Simulate view.
