# Spec 0027: Live v2 — dashboard, team relay, automatic run log

- **Status:** approved (owner decisions 2026-10-09, Daniel Hodeib: dashboard + backend relay; relay at
  10 Hz adjustable; stream saved as a run log; shared automatically when logged in, switch to turn it off)
- **Owner:** Daniel Hodeib
- **Plan section:** docs/PLAN.md §7 (Live screen), §9 (live telemetry relay), milestone weeks 6–7
  ("Live tab + telemetry relay")
- **Depends on:** Spec 0005 (car runtime telemetry server), Spec 0006 (backend, workspace sync),
  Spec 0010 (engine car link, minimal Live tab), Spec 0014/0025 (quick tracks for the map)

## Purpose
The Live tab today shows a few numbers of one car to the person whose laptop is connected. Test days need
more: a dashboard that shows at a glance whether the car is healthy and what it sees, the same view for
teammates who are not standing next to the car, and every test drive kept automatically so it can be
analysed later (calibration, imitation learning, reports).

## Scope
- In scope:
  1. **Dashboard** in the Live tab (local and remote viewers):
     - health lights: link/latency, loop rate, deadline misses, battery, CPU temperature/load, faults;
     - rolling plots of the last 30 s: speed commanded vs measured, steering commanded vs measured,
       battery voltage, loop rate (small SVG plots, no new dependency);
     - state timeline of the last 60 s (one coloured bar per state);
     - top-down view: LiDAR points (`RangeArray`) and range sensors (`RangeReading`, as bars) around the car;
       with `pose_est`, the car's pose and trail drawn on a quick track chosen from the Tracks tab
       (centreline + corridor band);
     - drive timer (since the car first moved) and lap/lap time when the controller publishes the channels
       `lap` / `lap_time_s`;
     - alarms: thresholds per signal with defaults (loop rate < 40 Hz, battery < 7.0 V, CPU > 85 °C,
       latency > 100 ms, any new fault); a raised alarm shows a banner, adds an event and beeps (WebAudio,
       mutable); thresholds are stored per browser.
  2. **Team relay** through the backend: the engine connected to the car publishes the stream to the
     backend; every member of the workspace can list live sessions and watch one (read-only, no teleop,
     no stop, no notes).
  3. **Automatic run log**: the publishing engine records every frame and event at full rate and, when the
     session ends, saves it as a `run` object in the workspace (works offline; syncs later).
- Out of scope (later specs): Bluetooth/ESP-NOW transports and failover, bandwidth tiers on the car,
  replay of race logs and run comparison, camera stream, widget layout editor, state-machine diagram,
  policy explainability, remote stop, MCP `live_status`/`live_snapshot`.

## Interfaces (additive)
**Backend** (`/api/v1`, contract snapshot; no database change — live sessions are in memory):
- `WS /workspaces/{ws}/live/publish` — header `Authorization: Bearer …`, scope `sim_train`. First message
  `{"type": "start", "car": str, "rate_hz": float}` → `{"type": "session", "id": str}`. Then the engine
  sends car messages unchanged (`hello`, `telemetry`, `event`, `ack`) and `{"type": "link", …}`. Closing
  the socket ends the session.
- `GET /workspaces/{ws}/live` (scope `read`) → `list[LiveSession]`:
  `{id, workspace_id, car, publisher, started_at, last_message_at, messages}`.
- `WS /live/{session_id}/watch` — header auth, scope `read`, same workspace. The backend first sends
  `{"type": "session", …LiveSession}`, then the last `hello` and the last `telemetry` frame it has, then
  every message as it arrives; `{"type": "end"}` when the publisher leaves. Watchers' messages are ignored.
- Limits: 64 KB per message, 20 watchers per session, a publisher idle for 30 s is dropped. A slow watcher
  loses frames (bounded queue of 50, oldest dropped), never the publisher.
- Worker tokens (spec 0020) cannot publish or watch (scope).

**Engine** (local API, spec 0008):
- `/api/v1/car/live` connect message gets `share: bool = true` and `share_rate_hz: float = 10` (1–20).
  When `share` and the workspace is logged in, the engine opens the publish socket; telemetry frames are
  forwarded at most at `share_rate_hz` (the newest frame wins), all other messages always. The engine adds
  `{"type": "share", "state": "off" | "sharing" | "offline", "session": id | null}` messages for the UI.
  Without a backend the car link works exactly as before.
- On close, the engine writes `telemetry.jsonl.gz` (one car/engine message per line, with the engine's
  receive time `rx_t`) plus `notes.json` and saves them with the sync client as a fileset version of the
  `run` object `live-<car>-<YYYYMMDD-HHMMSS>` (message "test drive <car>, <minutes> min, <frames> frames").
  Sessions with no telemetry frame are not saved. The file is kept locally if saving fails.
- `GET /api/v1/workspace/live` → the backend's `list[LiveSession]`;
  `WS /api/v1/workspace/live/{id}/watch` → proxies the backend's watch socket to the UI.

## Behaviour
- Teleop, stop and notes stay local (laptop ↔ car); the backend never forwards anything to a car.
- Race mode: the car does not stream in race mode (spec 0005); nothing changes here.
- The dashboard works from `TelemetryFrame` fields only; missing fields show "–" and do not raise alarms
  (except faults).
- Remote viewers see the relay rate; the local viewer sees the car's full rate.

## Non-functional targets
- Local dashboard keeps up with 50 Hz frames on a MacBook Air M2 (plots render at most at 10 Hz).
- Remote latency car → teammate's screen < 1 s over Cloudflare (plan §9d: < 100 ms only on the local link).
- A 30-minute drive at 20 Hz gives a run log under 15 MB.

## Acceptance criteria (→ tests, critical paths only)
- [ ] AC1: Backend relay: a publisher's frames reach two watchers in order; a late watcher first gets the
  last `hello` and `telemetry`; the publisher closing sends `end` and removes the session from the list;
  a `read` token cannot publish, a worker token cannot watch, a watcher of another workspace gets 403/404.
- [ ] AC2: Engine: with a fake car at 50 Hz and `share_rate_hz` 10, the backend receives ≈10 frames/s and
  every event; after disconnecting, a `run` object with `telemetry.jsonl.gz` containing all 50 Hz frames
  exists in the workspace.
- [ ] AC3: Without login (or backend offline) the car link works as before and the UI gets
  `share: off|offline`.
- [ ] AC4 (frontend unit): alarm evaluation (thresholds, "new fault", missing values) and the rolling buffer.
- [ ] AC5 (manual, owner): a test drive with a second laptop watching through the team relay; the run log
  appears in the Team tab afterwards.
